1С → amoCRM: статус оплаты

Технический мануал для разработчика 1С. Описывает передачу агрегированного статуса счетов paid/unpaid, изменение карточки и ограничения по воронкам amoCRM.

Версия: 2.0 Дата: 07.08.2026 Базовый URL: http://api-avto-terminal.ru
Содержание 1. Логика обмена · 2. Контракт · 3. Метод API · 4. Повторная отправка · 5. Ошибки · 6. Ограничения · 7. Ручные тесты · 8. Принятые решения

1. Логика обмена

Главное правило: 1С самостоятельно определяет агрегированный статус счетов. API не получает перечень счетов и не пересчитывает оплату — он принимает по VIN одно из двух значений: paid или unpaid.
1С определяет, есть ли неоплаченные счета по автомобилю.
1С отправляет JSON с обязательными полями vin и status.
API ищет ровно одну сделку по полю VIN в подключённых воронках.
API приводит checkbox, цвет и при необходимости стадию к целевому состоянию.

Целевые значения основной воронки:

  • воронка: «Воронка», ID 7523034;
  • этап назначения: «Оплачено», ID 64577710.
  • «Счёт выставлен (Усс)»: 990217;
  • «Счёт оплачен (Усс)»: 990219.

2. Общий контракт запроса

Основной метод принимает JSON с VIN автомобиля и агрегированным статусом счетов.

HTTP-заголовки

Authorization: Bearer <SANCTUM_TOKEN>
Content-Type: application/json
Accept: application/json

Тело запроса

{
  "vin": "JTDBR32E720123456",
  "status": "paid"
}
Поле Тип Обязательное Ограничения
vin Строка Да Непустая строка, максимум 64 символа. Пробелы по краям удаляются, регистр приводится к верхнему.
status Строка Да Только точные значения paid или unpaid.
Не передавайте токен в JSON или query-параметрах. Токен передаётся только в заголовке Authorization. Не записывайте его в пользовательские логи 1С.

3. Метод API

POSThttp://api-avto-terminal.ru/api/amocrm/integrations/1c/payments/status
Метод изменяет карточку amoCRM. Значение unpaid отключает признак оплаты и красит карточку в красный; paid включает оба признака, красит карточку в зелёный и переводит открытую сделку в «Оплачено».

Пример curl

curl -X POST "http://api-avto-terminal.ru/api/amocrm/integrations/1c/payments/status" \
  -H "Authorization: Bearer SANCTUM_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"vin":"JTDBR32E720123456","status":"paid"}'

Временный адрес для обратной совместимости

POSThttp://api-avto-terminal.ru/api/amocrm/integrations/1c/payments/paid

Оба адреса ведут в одну логику. На старом адресе запрос только с VIN по-прежнему трактуется как paid. Если поле status передано, старый адрес также принимает paid/unpaid. Новую интеграцию следует строить на /payments/status; старый адрес является временным alias.

Целевые состояния

statusСчёт выставленСчёт оплаченЦветСтадия
unpaidАктивенНеактивенКрасныйНе меняется
paidАктивенАктивенЗелёный«Оплачено» для открытой сделки

Успешный ответ

Формат совпадает с ответами существующих методов dt-status и td-status:

{
  "message": "OK"
}

HTTP 200 и message=OK означают, что факт оплаты принят и обработан.

4. Повторная отправка

Вызов идемпотентен: API сравнивает checkbox, цвет и стадию с целевым состоянием и обновляет только отличающиеся значения. Если 1С не получила HTTP-ответ из-за обрыва сети, запрос с тем же VIN и status можно повторить.

{
  "message": "OK"
}

5. Ошибки и повторные попытки

HTTP Причина Что делать в 1С Автоповтор
401 Bearer-токен отсутствует, просрочен или неверен. Проверить настройку токена. Нет
404 Сделка с переданным VIN не найдена. Проверить VIN и наличие карточки в amoCRM. Нет
409 VIN найден более чем в одной сделке либо сделка находится не в основной воронке. Передать на ручную проверку. Не выбирать сделку автоматически. Нет
422 Поле vin/status отсутствует, нарушен формат или передан неизвестный статус. Исправить формирование JSON. Нет
502 amoCRM временно не ответила или не приняла обновление. Сохранить запрос в очередь повторной отправки. Да

Пример ответа с ошибкой:

{
  "error": "Сделка с VIN JTDBR32E720123456 не найдена"
}
Рекомендуемый автоповтор только для сетевой ошибки или HTTP 502: через 1 минуту, 5 минут и 15 минут. После трёх неудач — ручная проверка. Для 401, 404, 409 и 422 автоматический повтор без исправления причины бесполезен.

6. Ограничения по воронкам

На дату документа перевод в «Оплачено» реализован только для основной воронки. В двух остальных подключённых воронках такого этапа сейчас нет.
Воронка ID Этап «Оплачено» Результат запроса
Воронка (основная) 7523034 Есть ID 64577710 Боевой метод переводит сделку в «Оплачено».
Транзит по РФ 10944982 Нет HTTP 409; карточка не меняется.
Офис Москва 11036918 Нет HTTP 409; карточка не меняется.

Как выполняется поиск

  • API ищет VIN сразу в трёх перечисленных воронках.
  • Если VIN найден только в основной воронке, обработка продолжается.
  • Если VIN найден только в «Транзит по РФ» или «Офис Москва», возвращается 409.
  • Если одинаковый VIN найден в нескольких сделках или воронках, возвращается 409; API не выбирает карточку произвольно.

Чтобы включить оплату в двух остальных воронках, необходимо создать в каждой этап «Оплачено», получить его ID и добавить на backend маппинг pipelineId → paidStatusId. До этого 1С должна отправлять такие случаи на ручную обработку.

7. Набор ручных тестов

Важно: методы изменяют боевую amoCRM. Для проверки использовать специально подготовленные карточки с уникальными VIN и заранее записать их исходные поля, цвет и стадию.
  1. Новый URL, paid. На основной воронке выставить: «Счёт выставлен» = да, «Счёт оплачен» = нет, цвет красный, стадия «Оплата». Отправить paid. Ожидание: оба checkbox активны, цвет зелёный, стадия «Оплачено», HTTP 200.
  2. Повторный paid. Повторить тот же запрос. Ожидание: данные не меняются, HTTP 200.
  3. unpaid после paid. На карточку из предыдущего теста отправить unpaid. Ожидание: «Счёт выставлен» активен, «Счёт оплачен» выключен, цвет красный, стадия остаётся «Оплачено».
  4. Повторный unpaid. Повторить запрос. Ожидание: данные не меняются, HTTP 200.
  5. paid при выключенном «Счёт выставлен». Оба checkbox выключены. Ожидание: оба включены, цвет зелёный, стадия «Оплачено».
  6. unpaid при выключенном «Счёт выставлен». Ожидание: «Счёт выставлен» включён, «Счёт оплачен» выключен, цвет красный, стадия прежняя.
  7. Legacy URL без status. Отправить на /payments/paid только VIN. Ожидание: запрос обработан как paid.
  8. Legacy URL с unpaid. Передать VIN и status=unpaid. Ожидание: применяется логика unpaid.
  9. Закрытая сделка. На стадии 142 или 143 отправить paid, затем unpaid. Ожидание: checkbox и цвет меняются, закрытая стадия не меняется.
  10. Другая воронка. Отправить VIN сделки «Транзит по РФ» и отдельно «Офис Москва». Ожидание: HTTP 409, карточки не изменены.
  11. Дублирующий VIN. Один VIN находится в двух подключённых воронках. Ожидание: HTTP 409, ни одна карточка не изменена.
  12. Неизвестный VIN. Ожидание: HTTP 404.
  13. Ошибочный payload. Проверить отсутствие status на новом URL, значение partial, отсутствие VIN и status другого регистра. Ожидание: HTTP 422.
  14. Авторизация. Запрос без Bearer-токена и с неверным токеном. Ожидание: HTTP 401, карточка не изменена.

8. Потенциальные противоречия и принятая реализация

  • unpaid на стадии «Оплачено». Стадия не откатывается: checkbox оплаты выключается, карточка красится в красный, стадия остаётся «Оплачено».
  • Общий цвет с логикой ДТ. Последний статус оплаты считается приоритетным и может перезаписать цвет, установленный обработкой ДТ.
  • Закрытые стадии 142/143. Стадия не переоткрывается, но checkbox и цвет обновляются по данным 1С.
  • paid при выключенном «Счёт выставлен». Оба checkbox включаются: оплаченный счёт считается выставленным.
  • Фраза «всё остаётся как есть». Она применяется ко всему целевому состоянию, а не только к checkbox: если цвет или стадия не совпадают, они корректируются.
  • Название метода. Основным стал /payments/status; /payments/paid временно сохранён как совместимый alias.
Документ фиксирует контракт синхронизации оплаты и принятые решения на 07.08.2026. Старый адрес /payments/paid является временным alias и должен быть удалён после перехода 1С на /payments/status.
